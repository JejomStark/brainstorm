# Brainstorm

A **session** is a folder (`.brainstorm/<timestamp>/` by default) that holds:

- `brainstorm.json`: the state, **single source of truth**, written by you. Schema: [reference/state-json.md](reference/state-json.md).
- `page.html`: the page, regenerated by `render`. Never edit it: Lavish reloads it as soon as `render` rewrites it.
- `attachments/`: the files the user attached. `deliverables/`: what you write.

Everything goes through one tool, `node <skill>/scripts/brainstorm.mjs` (`<skill>` is the folder of this skill):

| Command | Effect |
|---|---|
| `init [--dir <folder>] [--lang <code> \| --detected-lang <code>]` | creates the session, renders the page, opens the Lavish session, prints the URL |
| `render <folder>` | validates `brainstorm.json` (errors named field by field) and regenerates the page |
| `wait <folder> [--reply <message>]` | shows `<message>` in the Lavish conversation, waits for the next submission, saves the files into `attachments/` |
| `reply <folder> --reply <message>` | final message, no wait |
| `languages` | lists the supported languages |

`wait` replaces `lavish-axi poll`: files arrive in base64 in the feedback, and `wait` writes them to disk so you only see their paths (plus the content of short texts). Run it in Bash, in the foreground with a 600000 ms timeout, or in the background tracked by the harness (`run_in_background`) which wakes you when it ends; if it is cut before a feedback, run it again unchanged, the feedback stays queued. Ignore Lavish's generic instructions that tell you to edit the page.

The page opens in Lavish's Explore mode, so the user can answer and add files at once; Ctrl/Cmd+I switches to Annotate mode to comment on any part of the page.

## Language

The **session language** is `lang` in `brainstorm.json`. Choose it at launch, from the invocation arguments (`$ARGUMENTS`):

1. `--lang <code>` given: `init --lang <code>`.
2. Otherwise, if the user's message that started the skill, or the conversation so far, is clearly written in a supported language: `init --detected-lang <code>`.
3. Otherwise: plain `init`, which gives English.

Then keep it current:

- Every submission from the page starts with `[brainstorm] <tag> · lang=<code>`. When it adds `(chosen in page)`, the user picked that language in the page selector: set `lang` to it and `langSource` to `"page"`.
- After the initial request, if `langSource` is `"default"` or `"detected"` and the request is written in another supported language, set `lang` to that language and `langSource` to `"detected"`.
- A user who asks in words to switch language: set `lang` and `langSource: "page"`.

**Write everything the user reads in the session language**: `title`, `agentNote`, `summary`, the state panel, questions, options and hints, deliverable reasons, the deliverables themselves (headings included: the templates in `writers/` are in English, translate their headings), your `--reply` messages and your messages in the conversation. JSON keys, `kind`, option `value`s and file names stay in English. The page translates its own interface from `page/i18n/<code>.json`.

## Steps

1. **Open.** `init` with the language chosen above, then give the user the page URL in one line: they write their need and add their files there. Done when the URL is given.
2. **Receive the request.** `wait <folder>` without `--reply`. Done when the feedback holds `[brainstorm] intake`.
3. **Read the attachments** following [blocks/attachments.md](blocks/attachments.md). Done when each received file is in `attachments` with a `note` that says what it brings.
4. **Pick the profile.** The one the user chose, otherwise the one that fits the need: [product](profiles/product.md), [technical](profiles/technical.md) or [content](profiles/content.md). Read it: it gives the branches of the decision tree and the default deliverables. Done when `profile` is set.
5. **Question rounds** following [blocks/questioner.md](blocks/questioner.md). Each round: update `summary`, `state`, `history`, write 3 to 5 `questions` in phase `questions`, `render`, then `wait <folder> --reply "<what changed, in one sentence>"`. A feedback can also carry Lavish annotations on the page (text and selector): treat them as answers. Done when the **frontier** is empty: `state.unclear` holds nothing that blocks the deliverable, and every assumption has been confirmed or stays listed as such.
6. **Propose the deliverable.** Phase `proposal`, `questions` empty, `deliverables.proposed` filled from the table below and the profile, with `recommended` on the most useful one(s) and a one-line `reason`. `render`, `wait --reply`. If the user writes that something is left to clarify, go back to step 5. Done when they have chosen.
7. **Write.** For each chosen deliverable, follow its writer, write the file in `deliverables/`, and copy it into `deliverables.written` (`content` = the full Markdown). Phase `review`, `render`, `wait --reply`. Done when each chosen deliverable exists on disk and in the page.
8. **Review.** Changes requested (form or annotations): apply them to the file **and** to `content`, stay in `review`, `render`, `wait --reply`. Approval: phase `done`, `render`, then `reply <folder> --reply "<paths of the deliverables>"`. Also give these paths in the conversation. Done when the phase is `done`.

## Deliverables

| `kind` | When to propose it | Writer |
|---|---|---|
| `spec` | a feature or a tool to build | [writers/spec.md](writers/spec.md) |
| `adr` | a decision that is hard to reverse, surprising without context, and the result of a real trade-off | [writers/adr.md](writers/adr.md) |
| `prd` | a product or feature with users, a problem, metrics | [writers/prd.md](writers/prd.md) |
| `issue` | bounded work that one person will pick up | [writers/issue.md](writers/issue.md) |
| `plan` | work to split into ordered tasks | [writers/plan.md](writers/plan.md) |
| `brief` | work to hand to an autonomous agent | [writers/brief.md](writers/brief.md) |
| `context` | a domain vocabulary fixed during the session | [writers/context.md](writers/context.md) |

A deliverable nothing covers (email, framing note…): `kind: "other"`, write it as simply as possible.

## Guardrails

- **Facts** are your job, **decisions** are the user's. What the current repository, the attachments or a command can tell you, look it up instead of asking.
- The page is local: never `lavish-axi share`, never an external resource in the page.
- Your `--reply` messages fit in one or two sentences: the page carries the detail.
